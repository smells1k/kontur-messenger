# Архитектура «Контура»

## Общая картина

```
                 ┌──────────────────────── server ─────────────────────────┐
  браузер / .exe │                                                        │
  ┌───────────┐  │  express  ── REST /api/*, /uploads/*, статика web/      │
  │  app.js   │──┼─▶                                                        │
  │  call.js  │  │  ws (WebSocket) ── доставка, присутствие, синхронизация │
  └───────────┘  │  core.js ── бизнес-логика (чаты, сообщения, звонки)     │
                 │  store.js ── JSON-база + журнал событий                │
                 │  bots.js  ── встроенный помощник                        │
                 └────────────────────────────────────────────────────────┘
        ▲                        ▲                       ▲
        │  WebRTC (P2P, медиа)   │  WebRTC-сигналинг     │  синхронизация
        └────────────────────────┴───────────────────────┘
```

## Модули сервера

| Файл | Ответственность |
|---|---|
| `server.js` | конфигурация (флаги/ENV), сборка сервисов, раздача веб-клиента, graceful shutdown |
| `src/store.js` | JSON-хранилище с отложенной атомарной записью, индексы, журнал событий `events`, отметки прочтения |
| `src/core.js` | чаты, сообщения, реакции, закрепления, «печатает», прочтения, звонки (жизненный цикл) |
| `src/realtime.js` | WebSocket-слой: авторизация по токену, доставка событий, присутствие, синхронизация, сигналинг |
| `src/api.js` | REST: вход/регистрация, профиль, чаты, история, поиск, загрузка файлов |
| `src/bots.js` | бот-помощник: команды, ответы, «живые» сообщения в демо-группе |
| `src/seed.js` | демо-данные: 4 пользователя, бот, 2 группы, 3 личных чата, история, реакции, файл |
| `src/util.js` | id, scrypt-пароли, JWT (HS256), цвета аватаров, очистка текста |

## Хранилище

Одна JSON-база (`data/db.json`), запись — атомарная (`tmp` + `rename`), с задержкой 200 мс
(несколько изменений подряд = одна запись). Горячие индексы держатся в памяти:

```js
users[id]            // пользователи (пароли — scrypt+salt)
chats[id]            // чаты: тип, участники, админы, закрепления
messages[id]         // сообщения
chatMessages[chatId] // порядок сообщений в чате
reads["chatId:userId"] // отметки прочтения
calls[id]            // активные звонки (не переживают перезапуск)
events[]             // журнал для синхронизации: {seq, users[], type, payload, ts}
```

Почему JSON, а не SQLite? Ноль зависимостей, простые бэкапы (скопировать папку), предсказуемое
поведение при 10–100k сообщений. Для больших объёмов точку расширения видно сразу — `store.js`
изолирует всё хранилище, достаточно заменить его методы.

## Синхронизация

Ключевая идея — **журнал событий с монотонным номером** (`seq`), а не «умные» диффы:

1. Любое изменение проходит через `Core.emit(userIds, type, payload)`:
   - пишет событие в `events` с новым `seq`;
   - сразу отправляет его всем подключённым получателям.
2. Клиент применяет **одну и ту же функцию** `applyRemote(type, payload)` для «живых» событий
   и для событий из догонки — поэтому состояние одинаково независимо от того, был клиент онлайн или нет.
3. При старте клиент отправляет `sync {since}` (последний применённый `seq` из localStorage).
4. Сервер отдаёт события пользователя с `seq > since` пачками по 500 штук, затем `sync:done`.
5. Клиент держит локальный кэш последних 300 сообщений чата в IndexedDB — чат открывается
   мгновенно, а затем уточняется с сервера.

Что даёт такая схема: догон после долгого офлайна, несколько устройств под одним аккаунтом,
устойчивость к переподключениям (WS падает → клиент переподключается с экспоненциальной задержкой
и снова догоняет журнал), отсутствие гонок «кто прав» — порядок задаёт сервер.

Не в журнале: `typing`, `presence`, `call:signal` — эфемерные события, они не нужны задним числом.

## Офлайн-отправка

Если WebSocket недоступен, `sendMessage()` кладёт payload в офлайн-очередь (`localStorage.k.outbox`),
а в интерфейсе показывает сообщение с «часиками». При подключении очередь отправляется в порядке
появления, `message:ack` подменяет временный id на серверный.

## Прочтения и галочки

`reads[chatId:userId].lastMessageId` — «до какого сообщения дочитано». Событие `read` рассылается
всем участникам, поэтому автор видит `✓` (доставлено) и `✓✓` (кто-то дочитал). Счётчик непрочитанных —
это число сообщений после `lastMessageId`, не своих и не удалённых.

## Звонки

Mesh-топология (каждый с каждым), поэтому подключение простое и не требует медиасервера:

- **сигналинг** — через тот же WebSocket (`call:signal`), SDP/ICE не хранятся;
- **инициатор**: `call:invite` → сервер рассылает `call:incoming` участникам чата;
- **подключение**: `call:join` → сервер отвечает `existingPeers`; оффер делает участник с бóльшим id
  (детерминированно, чтобы не было «двойных офферов» при одновременном входе);
- **медиа**: `getUserMedia` → `addTrack` в каждый `RTCPeerConnection`, далее стандартный обмен оффер/ответ/ICE;
- **состояния**: `call:state` (микрофон, камера, демонстрация) рассылается всем — рисуем значки и плитки;
- **демонстрация экрана**: `getDisplayMedia`, затем `sender.replaceTrack(screenTrack)` без пересогласования;
- **эффекты картинки**: video → canvas (`captureStream`) → `replaceTrack`, поэтому эффект видят все;
- **STUN**: публичные Google/Cloudflare — достаточно для большинства домашних сетей; свой TURN
  добавляется в массив `ICE` в `web/js/call.js` (для симметричных NAT);
- **выход из звонка при разрыве**: если у пользователя не осталось соединений, сервер убирает его из звонка.

## Веб-клиент

Без сборки и фреймворков: `index.html` + `css/style.css` + три JS-файла.

- `app.js` — состояние (`S`), соединение (`conn`), REST-обёртка, рендер списка чатов и ленты
  сообщений, вложения, эмодзи, панели, модалки, очередь, уведомления, звуки.
- `call.js` — отдельный модуль звонков; общается с сервером тем же сокетом через `window.__konturSend`,
  а события получает из `app.js` (switch по `call:*`).
- `emoji-data.js` — 1870 эмодзи с русскими и английскими ключевыми словами (генерируется из `emoji-datasource`).

Рендер простой и предсказуемый: перерисовка списка сообщений целиком при изменении
(лента виртуализируется «на глаз» — грузим по 60 сообщений и дорисовываем по скроллу вверх),
поэтому код остаётся читаемым, а на практике до сотен сообщений в чате всё работает без задержек.

## Десктопная сборка

- `release/KonturServer.exe` — `pkg`-сборка лаунчера: внутрь зашиты Node.js, сервер и веб-клиент.
  Лаунчер находит `web/` рядом с `.exe` (или распаковывает встроенную копию в профиль пользователя),
  поднимает сервер, ждёт `/health` и открывает окно через Edge/Chrome в режиме `--app`.
- `desktop/` — Electron-приложение: окно без браузерной обвязки, меню, настройки адреса сервера,
  разрешения на камеру/микрофон и системный выбор источника для демонстрации экрана.
  Если локальный сервер не найден, клиент запускает его сам (тот же код сервера из ресурсов приложения).

## Безопасность (для локальной сети)

- пароли: `scrypt` + случайная соль;
- сессии: JWT HS256, секрет `data/secret.key` (создаётся при первом запуске, права `600`);
- доступ к чатам проверяется на каждом действии (участник ли пользователь);
- чужие чаты отдают `403/404`, файлы — по прямой ссылке внутри сервера;
- для интернета: HTTPS-прокси (nginx/Caddy) + `wss://`, флаг `--closed`, лимиты загрузки;
  при желании легко добавить allow-list IP на уровне прокси.
